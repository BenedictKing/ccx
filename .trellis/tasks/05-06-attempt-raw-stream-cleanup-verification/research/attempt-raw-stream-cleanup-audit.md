### Shared attempt lifecycle

`TryUpstreamWithAllKeys` is the authoritative attempt loop for Messages, Chat, Responses, and Gemini proxy families. It selects each BaseURL/key attempt, prepares the per-attempt request body, restores it into Gin context, builds a request, records channel log/metrics start, sends the upstream request, classifies non-2xx responses, delegates 2xx handling to the protocol `handleSuccess`, and finalizes metrics/channel logs (`backend-go/internal/handlers/common/upstream_failover.go:158`, `backend-go/internal/handlers/common/upstream_failover.go:250`, `backend-go/internal/handlers/common/upstream_failover.go:272`, `backend-go/internal/handlers/common/upstream_failover.go:443`, `backend-go/internal/handlers/common/upstream_failover.go:525`).

The control-plane contract is already explicit: `HandleSuccessFunc` implementors must close `resp.Body` themselves (`backend-go/internal/handlers/common/upstream_failover.go:43`). Non-2xx upstream responses are read and closed before failover classification (`backend-go/internal/handlers/common/upstream_failover.go:301`, `backend-go/internal/handlers/common/upstream_failover.go:303`). Send-time `context.Canceled` finalizes as client cancel and stops failover (`backend-go/internal/handlers/common/upstream_failover.go:272`, `backend-go/internal/handlers/common/upstream_failover.go:276`, `backend-go/internal/handlers/common/upstream_failover.go:282`). Handler-time `context.Canceled` also finalizes as client cancel and stops failover (`backend-go/internal/handlers/common/upstream_failover.go:443`, `backend-go/internal/handlers/common/upstream_failover.go:447`, `backend-go/internal/handlers/common/upstream_failover.go:452`).

Preflight or parse failures returned as `ErrEmptyStreamResponse` or `ErrInvalidResponseBody` are treated as retryable before the client response is committed (`backend-go/internal/handlers/common/upstream_failover.go:453`, `backend-go/internal/handlers/common/upstream_failover.go:465`). In-stream preflight cooldown and blacklist sentinel errors are also ccx-owned failover decisions: cooldown calls `MarkKeyAsFailedWithDuration`, blacklist can call `BlacklistKey`, both finalize the failed attempt and continue to the next key (`backend-go/internal/handlers/common/upstream_failover.go:466`, `backend-go/internal/handlers/common/upstream_failover.go:473`, `backend-go/internal/handlers/common/upstream_failover.go:482`, `backend-go/internal/handlers/common/upstream_failover.go:492`).

Multi-channel failover remains outside forwarding builders. `HandleMultiChannelFailover` checks client cancellation before each channel attempt, delegates selected-channel work, only sets trace affinity for real success, and otherwise marks the channel failed (`backend-go/internal/handlers/common/multi_channel_failover.go:62`, `backend-go/internal/handlers/common/multi_channel_failover.go:65`, `backend-go/internal/handlers/common/multi_channel_failover.go:88`, `backend-go/internal/handlers/common/multi_channel_failover.go:93`, `backend-go/internal/handlers/common/multi_channel_failover.go:100`).

### Shared raw fan-out lifecycle

The shared raw fan-out helper is `startRawStreamFanout`. It creates an attempt-scoped goroutine, reads raw SSE events from `resp.Body`, sends copied raw bytes and text onto a bounded channel, closes `eventChan`, `errChan`, and `done` on exit, closes the provider response body, and installs a cancellation watcher that closes the body when the attempt context is cancelled (`backend-go/internal/handlers/common/stream.go:517`, `backend-go/internal/handlers/common/stream.go:523`, `backend-go/internal/handlers/common/stream.go:526`, `backend-go/internal/handlers/common/stream.go:527`, `backend-go/internal/handlers/common/stream.go:541`, `backend-go/internal/handlers/common/stream.go:560`).

The cleanup helper `cleanupRawStreamFanout` cancels the attempt, starts draining the raw event/error channels, and waits up to 5 seconds for the fan-out `done` signal (`backend-go/internal/handlers/common/stream.go:594`, `backend-go/internal/handlers/common/stream.go:596`, `backend-go/internal/handlers/common/stream.go:598`). This is the helper later implementation work should reuse for any same-format raw stream attempt that may fail over.

Risk note: `drainRawStreamChannels` launches background drain goroutines with a 60 second timeout and `cleanupRawStreamFanout` waits only up to 5 seconds for `done` (`backend-go/internal/handlers/common/stream.go:474`, `backend-go/internal/handlers/common/stream.go:476`, `backend-go/internal/handlers/common/stream.go:594`, `backend-go/internal/handlers/common/stream.go:599`). This is much better than starting the next attempt without waiting, but it is still a bounded best-effort cleanup rather than a hard guarantee that a wedged upstream body is gone before retry.

### Client cancel risk points

- Shared failover correctly treats only `context.Canceled` as client cancel and does not blacklist/cooldown keys for that case (`backend-go/internal/handlers/common/upstream_failover.go:24`, `backend-go/internal/handlers/common/upstream_failover.go:31`, `backend-go/internal/handlers/common/upstream_failover.go:447`).
- Shared raw helper paths return `context.Canceled` on client context cancellation and suppress SSE error writes for `context.Canceled` (`backend-go/internal/handlers/common/stream.go:1315`, `backend-go/internal/handlers/common/stream.go:1317`, `backend-go/internal/handlers/common/stream.go:1323`, `backend-go/internal/handlers/common/stream.go:1415`, `backend-go/internal/handlers/common/stream.go:1417`, `backend-go/internal/handlers/common/stream.go:1423`).
- Non-shared local stream loops are inconsistent: Chat `streamPassthrough` ignores `c.Writer.Write` errors (`backend-go/internal/handlers/chat/handler.go:800`); Responses converted stream marks `clientGone` but continues upstream read and returns success metrics (`backend-go/internal/handlers/responses/handler.go:880`, `backend-go/internal/handlers/responses/handler.go:883`, `backend-go/internal/handlers/responses/handler.go:946`); Gemini conversion loops generally ignore write errors (`backend-go/internal/handlers/gemini/stream.go:179`, `backend-go/internal/handlers/gemini/stream.go:427`).
- Because upstream requests are built with `c.Request.Context()` in Chat and Gemini (`backend-go/internal/handlers/chat/handler.go:350`, `backend-go/internal/handlers/gemini/handler.go:441`), cancellation may still interrupt upstream reads. The risk is that several local loops do not deliberately close the body, cancel the attempt, or return `context.Canceled` at the stream helper boundary, so shared metrics/failover cannot reliably classify them as client cancel.

### Preflight error risk points

- Shared Messages raw and generic raw helpers preflight before headers. They can safely return `ErrInvalidResponseBody`, `ErrCooldownKey`, `ErrBlacklistKey`, or `ErrEmptyStreamResponse` to `TryUpstreamWithAllKeys` without committing client headers (`backend-go/internal/handlers/common/stream.go:1245`, `backend-go/internal/handlers/common/stream.go:1281`, `backend-go/internal/handlers/common/stream.go:1349`, `backend-go/internal/handlers/common/stream.go:1385`).
- Shared raw preflight buffers are bounded by `maxRawStreamPreflightBufferBytes`, and individual raw events are bounded by `maxRawStreamEventBytes` (`backend-go/internal/handlers/common/stream.go:71`, `backend-go/internal/handlers/common/stream.go:73`, `backend-go/internal/handlers/common/stream.go:560`, `backend-go/internal/handlers/common/stream.go:1503`).
- Responses raw passthrough has no preflight at all: it forwards response headers and status before reading a single byte (`backend-go/internal/handlers/responses/handler.go:957`, `backend-go/internal/handlers/responses/handler.go:962`). This violates the target raw stream contract from the backend spec for empty stream, invalid raw event, cooldown, or blacklist failover-before-header.
- Chat non-Claude compatibility stream and Gemini cross-format streams also write headers before validation (`backend-go/internal/handlers/chat/handler.go:730`, `backend-go/internal/handlers/gemini/stream.go:39`). These are not target same-format raw paths except Chat compatibility defaults, but builder work must not copy this pattern into same-format raw forwarding.

### In-stream cooldown/blacklist risk points

- Shared raw preflight uses `DetectStreamFailoverAction`, which can produce cooldown or blacklist actions before headers (`backend-go/internal/handlers/common/stream.go:219`, `backend-go/internal/handlers/common/stream.go:1509`). `TryUpstreamWithAllKeys` owns applying cooldown, blacklist, metrics failure classes, URL failure, channel log completion, and retry (`backend-go/internal/handlers/common/upstream_failover.go:466`, `backend-go/internal/handlers/common/upstream_failover.go:473`, `backend-go/internal/handlers/common/upstream_failover.go:482`, `backend-go/internal/handlers/common/upstream_failover.go:501`).
- After headers are committed, shared raw helpers only write an SSE error for non-cancel errors and return the error (`backend-go/internal/handlers/common/stream.go:1315`, `backend-go/internal/handlers/common/stream.go:1318`, `backend-go/internal/handlers/common/stream.go:1415`, `backend-go/internal/handlers/common/stream.go:1418`). At that point safe failover is no longer possible, and `TryUpstreamWithAllKeys` will treat a non-sentinel stream processing error as a retryable channel failure but return handled=true (`backend-go/internal/handlers/common/upstream_failover.go:513`, `backend-go/internal/handlers/common/upstream_failover.go:522`).
- Responses converted stream detects blacklist during preflight only; it does not produce cooldown sentinel errors (`backend-go/internal/handlers/responses/handler.go:665`, `backend-go/internal/handlers/responses/handler.go:748`, `backend-go/internal/handlers/responses/handler.go:755`). Responses raw stream detects neither blacklist nor cooldown in the raw copy loop.

### Empty stream risk points

- Shared Messages raw stream returns `ErrEmptyStreamResponse` before headers for empty raw stream (`backend-go/internal/handlers/common/stream.go:1269`, `backend-go/internal/handlers/common/stream.go:1272`).
- Shared Chat/Gemini raw helper returns `ErrEmptyStreamResponse` before headers for empty raw OpenAI Chat/Gemini streams (`backend-go/internal/handlers/common/stream.go:1373`, `backend-go/internal/handlers/common/stream.go:1376`).
- Responses converted stream has a preflight empty check before headers (`backend-go/internal/handlers/responses/handler.go:745`, `backend-go/internal/handlers/responses/handler.go:752`).
- Responses raw stream cannot fail over on empty stream today because it commits headers/status first and then reads `resp.Body` (`backend-go/internal/handlers/responses/handler.go:957`, `backend-go/internal/handlers/responses/handler.go:968`, `backend-go/internal/handlers/responses/handler.go:980`). It will finish with nil usage/error on an empty body, causing shared failover to finalize success (`backend-go/internal/handlers/responses/handler.go:987`, `backend-go/internal/handlers/common/upstream_failover.go:525`).
- Chat non-Claude compatibility stream and Gemini conversion streams also lack empty-stream preflight. They return nil usage and nil error on empty upstream scans/reads, so shared failover sees success (`backend-go/internal/handlers/chat/handler.go:805`, `backend-go/internal/handlers/chat/handler.go:810`, `backend-go/internal/handlers/gemini/stream.go:86`, `backend-go/internal/handlers/gemini/stream.go:116`).

### Helpers later implementation should change

- Prefer extending/reusing `startRawStreamFanout`, `cleanupRawStreamFanout`, and `handleRawStreamPassthrough` in `backend-go/internal/handlers/common/stream.go` for same-format raw stream cleanup. These already centralize cancellation, body close, bounded buffering, preflight, and done wait.
- Add a Responses raw stream path that uses the shared raw fan-out/preflight lifecycle, or extract a protocol-neutral raw copy helper from `handleRawStreamPassthrough` that lets Responses keep raw bytes and its side-channel `rawResponsesStreamUsageCollector`. The implementation should preflight before `ForwardResponseHeaders` and return `ErrEmptyStreamResponse`, `ErrInvalidResponseBody`, `ErrCooldownKey`, or `ErrBlacklistKey` to `TryUpstreamWithAllKeys` while the response is uncommitted.
- Consider migrating Chat non-Claude direct compatibility stream and Gemini local conversion stream loops only if they are in scope for a later cleanup task. At minimum, they should not be used as templates for same-format raw forwarding because they do not preflight, do not wait on fan-out, and do not consistently return `context.Canceled`.
- If provider-normalized Messages stream cleanup needs stronger guarantees, the provider interface would need an explicit done/wait lifecycle. Do not bolt raw fan-out cleanup onto provider event channels without changing the provider contract, because `drainChannels` currently has no done channel.

### Helpers later implementation should not change

- Do not move scheduler, key selection, BaseURL retry, trace affinity, key cooldown, blacklist, circuit breaker, channel log terminal states, or metrics success/failure/client-cancel finalization into a forwarding builder. These remain ccx control-plane responsibilities in `HandleMultiChannelFailover` and `TryUpstreamWithAllKeys` (`backend-go/internal/handlers/common/multi_channel_failover.go:74`, `backend-go/internal/handlers/common/upstream_failover.go:220`, `backend-go/internal/handlers/common/upstream_failover.go:227`, `backend-go/internal/handlers/common/upstream_failover.go:395`, `backend-go/internal/handlers/common/upstream_failover.go:525`).
- Do not change `TryUpstreamWithAllKeys` response classification unless a cleanup helper needs to return an existing sentinel error more consistently. The current sentinel mapping is the boundary where raw stream preflight decisions become ccx cooldown/blacklist/failover side effects.
- Do not replace protocol converters or cross-format stream conversion as part of raw cleanup. Builder work should keep data-plane construction separate from schema conversion and from ccx control-plane finalization.
- Do not add channel-level compatibility switches for raw passthrough cleanup. The existing target contract is format-based passthrough with ccx control-plane failover.

### ccx control-plane boundary

The audit conclusion is explicit: ccx control plane is still owned by existing failover and metrics finalize code. The forwarding builder should only prepare outbound data-plane requests and response strategies. It must not finalize metrics, record cooldown/blacklist, retry keys, pick channels, manage circuit breakers, or decide trace affinity. Those responsibilities are already implemented in `HandleMultiChannelFailover` and `TryUpstreamWithAllKeys` (`backend-go/internal/handlers/common/multi_channel_failover.go:88`, `backend-go/internal/handlers/common/multi_channel_failover.go:93`, `backend-go/internal/handlers/common/upstream_failover.go:266`, `backend-go/internal/handlers/common/upstream_failover.go:286`, `backend-go/internal/handlers/common/upstream_failover.go:473`, `backend-go/internal/handlers/common/upstream_failover.go:492`, `backend-go/internal/handlers/common/upstream_failover.go:525`).

- I did not run backend tests because the requested output is an audit artifact only, not implementation verification.
- The current shared raw cleanup helper waits up to 5 seconds for fan-out completion; this is bounded cleanup, not an infinite wait. A future implementation should decide whether that timeout is acceptable or whether tests should assert immediate body close under controlled conditions only.
- Responses raw stream is the main mismatch with the target raw stream contract: it currently has no preflight, no cancellation helper, no fan-out done wait, no empty-stream failover, and no cooldown/blacklist detection before headers.
- Chat non-Claude compatibility streams and Gemini cross-format streams have weaker client-cancel/error handling, but they are not the same-format raw passthrough core targeted by the forwarding builder migration. Treat them as separate cleanup candidates unless a later task explicitly broadens scope.
