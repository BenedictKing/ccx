# 逻辑渠道下的协议级模型映射：现状与实施方案

## 目标与结论

渠道表示站点或账号，协议成员表示该账号下的执行路由。显式模型映射按**执行协议成员**配置和生效；精确优先、最长子串匹配等算法共用。跨协议联邦选中目标成员后，使用目标成员的映射，不把入口协议的映射广播到兄弟成员。Images、Vectors 保持原生协议边界。

本方案只处理显式 `modelMapping` 的作用域、管理和可见性；自动画像选模、协议转换和全量 Channel 数据模型迁移不在本轮范围。

## 已核对的现状

| 位置 | 当前行为 | 与目标的关系 |
| --- | --- | --- |
| `config/channel_authoritative.go` | `ChannelV3.Protocols[]` 每项保存完整 `UpstreamConfig`，加载时投影为六数组 | 已具备协议成员级持久化，无需新增映射表或迁移历史数据 |
| `config/model_mapping.go` | 从选中 `UpstreamConfig.ModelMapping` 读取；精确优先，否则最长子串，未命中透传 | 算法已共用，配置并非整张逻辑渠道卡共享 |
| `config/logical_channel_crud.go`、`handlers/logicalchannels` | 创建/更新请求可对每个 `protocols[].modelMapping` 单独赋值；更新时缺省为保留，空对象可清空 | 写入能力基本具备 |
| `handlers/{chat,gemini,images,vectors}`、`providers/*` | 发送路径按所选物理上游应用映射 | 多协议调用共用函数，但读取各自成员的值 |
| `LogicalChannelProtocol` 与 Web/Desktop 类型 | 聚合列表中的协议引用不包含映射；编辑弹窗绑定单条渠道 `form.modelMapping` | 单卡可编辑，统一视图无法直接比较和编辑兄弟协议映射 |
| `frontend/src/stores/channel.ts` | 托管账号编辑将账号共享字段和单卡字段分流，后者按 `channelUid` 更新 | 协议映射应保持单卡更新，不能随账号共享字段级联 |

因此，先前“不同协议混用一套”的描述仅对**匹配算法**成立；当前存储和生效范围已按物理协议成员隔离。设计文档中“六数组为权威”的早期表述也已过时：当前 `ChannelsV3` 是落盘权威，六数组是运行时投影。

## 尚存差距与风险

1. 统一渠道卡展示多个协议，但映射编辑仍须进入某一物理成员；用户容易把单卡映射误认为全账号生效。
2. 聚合 API 的 `LogicalChannelProtocol` 只携带引用和状态，不提供映射摘要；界面无法提示兄弟协议存在不同目标模型。
3. `modelMapping` 的匹配键仅是模型字符串，不含协议。若未来将它上移到 `LogicalChannel.Settings`，同名源模型在不同协议指向不同目标时会冲突。
4. 逻辑渠道 `PUT` 的协议更新采用可选 map：未传与 `{}` 的含义不同；客户端必须保留这个语义，并避免发送整个旧协议快照覆盖并发修改。
5. 自动托管渠道的显式映射编辑受界面门控；即使展示摘要，也不能暗示所有托管成员都允许手动覆盖。

## 分阶段实施

### 阶段 1：明确契约与后端回归

- 文档化“入口协议、执行协议、映射所属成员”三者关系；明确先选择执行成员，再应用该成员显式映射，自动画像解析只在现有门控下处理未命中项。
- 为同一逻辑渠道的 Chat/Responses 成员配置相同源模型、不同目标模型，验证各自直连、跨协议联邦、保存重载均取执行成员映射；补充未传保留、`{}` 清空、不同账号隔离用例。
- 核对 `ModelResolver`、候选枚举与发送路径对映射结果的一致性；若发现重复应用或映射后再次链式解析，只修具体调用点。

### 阶段 2：统一管理入口

- 在逻辑渠道详情中列出协议成员及其映射摘要，按协议成员进入编辑；源模型与目标候选从该成员可用模型取得，并展示执行协议名称。
- 保存时用稳定 `channelUid` 定位单个成员，提交差量 `modelMapping`；未编辑不发送，用户清空发送 `{}`。如统一 API 不能无歧义地按成员 UID 更新，则沿用现有 `/api/channels/:uid` 单成员更新入口。
- Web 与 Desktop 两套界面采用同一作用域和提示语；复制到其他协议只能由用户显式选择目标成员，逐项预览后提交，不提供默认广播。

### 阶段 3：收敛与验收

- 保留旧六类管理 API 与现有 `channelsV3.protocols[].upstream.modelMapping` JSON 兼容；不做数据迁移或 schema bump。
- 验证创建、更新、清空、保存重载、兄弟成员互不影响、托管账号编辑权限，以及跨协议请求实际发送的模型名。前端完成类型检查、测试、构建和两套编辑界面的手工走查。
- 发布前从现有配置备份抽样对比各成员映射；出现问题时回退界面入口即可，后端仍按原协议成员存储和路由。

完成标准：用户在一张逻辑渠道卡内能识别并编辑每个协议成员的映射；同名源模型可按协议指向不同目标；旧配置和旧 API 行为保持不变。
