# 子代理默认模型与独立渠道调度实施计划

日期：2026-11-19

状态：已实施；配置/API、四文本协议执行、Web/Desktop 独立 Tab、迁移保护及驾驶舱收敛已完成。

代码基线：`codex/v3-lean-from-2.9.37` / `e60a1eac`，发布版本 `v2.10.0`。

## 1. 目标与范围

核心目标：配置一次，让主代理继续使用原模型，子代理自动使用用户指定的较次级模型和独立渠道序列，省去驾驶舱中的逐会话接管与排序。

示例：主代理请求 `astra`；Responses 子代理默认模型设置为 `sol`，渠道顺序为「便宜渠道 A → 备用渠道 B」。实际模型通过各渠道已有模型映射解析，主代理继续按普通渠道策略执行。

本次范围：

- 在渠道列表增加「普通请求｜子代理」tab，子代理默认模型、参与开关和拖动排序集中在该页。
- 四类文本协议 `messages`、`responses`、`chat`、`gemini` 分别保存策略；只有精确识别出的子代理请求应用策略。
- 优先验收 Codex Responses 和 Claude Code Messages；Chat/Gemini 接入同一规则，但不宣称没有角色标记的客户端会自动识别。
- Web 与 Desktop 同步配置入口和行为，避免后台支持而桌面端仍需驾驶舱操作。
- 在替代流程完成后收敛驾驶舱；请求日志承担角色、实际模型、选路和失败原因观察。

本次不扩展成本自动评分、AI 判断任务难度、每会话模型规则、每渠道子代理模型例外或子代理专用 Key。`images`、`vectors` 保持原界面和调度。

设计约束：复用现有模型发现、映射、能力筛选和故障转移；统一策略解析入口，不复制一套调度器。子代理开关、排序属于持久默认策略，不需要 TTL。

## 3. 页面交互

保留协议导航，在文本协议的渠道列表上方增加「普通请求｜子代理」。默认打开普通请求；Web 可用 `?tab=subagent` 深链接，切换协议后重新加载对应策略。

子代理 tab 的内容：

| 区域 | 控件与行为 |
|---|---|
| 顶部 | 默认模型 combobox；第一项「保持原请求模型」，提供已有模型大类及手动输入具体模型名 |
| 渠道行 | 拖动手柄、顺序、名称、子代理参与开关、映射后模型预览、可用状态 |
| 页尾 | 「保存」「取消」；保存期间禁用重复提交，成功后展示服务端返回的真实配置 |

操作流程：

1. 进入子代理 tab，加载策略及当前渠道；未转换的旧配置显示兼容状态。
2. 选择默认模型、开启目标渠道、拖动调整顺序；这些操作只修改本页草稿。
3. 模型大类优先来自现有模型选项；具体模型按需复用渠道的 models 接口，展示来源渠道，不同时自动探测所有上游。
4. 每行显示该渠道最终会发送的模型；无法确认能力时显示「未验证」，不把未知模型标记成可用。
5. 点击保存，原子更新该协议策略；刷新后保留模型、开关和顺序。
6. 保存失败保留草稿；并发配置冲突提示重新加载后合并，禁止悄悄覆盖。

边界交互：

- 搜索时禁止拖动，避免部分可见列表覆盖完整顺序；关闭参与的渠道仍可见并保留位置。
- 尚无渠道时沿用添加渠道入口；已有渠道但全部关闭时展示「子代理暂无可用渠道」，允许明确保存这一状态。
- 普通请求开关与子代理参与开关独立；共享暂停、熔断、Key 禁用等状态用只读状态展示。
- 切换协议、tab 或离开页面时处理未保存草稿；模型列表异步更新保持行布局和已输入值。
- 移动端除拖动外提供上移/下移按钮，键盘可操作开关和排序。
- 两端表单、类型、i18n、图标注册保持一致；不给子代理 tab 加驾驶舱接管、会话排序或重复说明。

## 4. 配置与管理接口

建议在 `Config` 新增 `subagentRouting`，以文本协议为 key。策略不存在表示旧行为兼容；策略存在表示该协议已经启用独立调度。示例 UID 为占位值：

```json
{
  "subagentRouting": {
    "responses": {
      "model": "sol",
      "channels": [
        { "channelUid": "uid-a", "enabled": true },
        { "channelUid": "uid-b", "enabled": true },
        { "channelUid": "uid-c", "enabled": false }
      ]
    }
  }
}
```

字段规则：

- `model` 为空表示保持原请求模型；具体值先 trim，再通过已有映射解析，不固定绑定厂商模型。
- `channels` 数组顺序即子代理顺序，不另存 `priority`；引用现有 `ChannelUID`，请求执行时再解析当前 index。
- 未列出的渠道不参与独立策略；新增或复制渠道分配独立 UID，默认追加且关闭，避免新上游自动接收子代理流量。
- 删除渠道同步清理引用；普通渠道重排、改名和换 Key 不改变子代理顺序。
- `enabled` 控制子代理参与。新策略中普通 `status=disabled` 不排除已启用的子代理渠道；`suspended`、Key 禁用、熔断等共享运行限制继续生效。
- 旧 `SubagentModel` 仅作为未转换协议的兼容输入；已启用新策略时不再作为例外覆盖统一模型。

管理接口：

| 方法与路径 | 用途 |
|---|---|
| `GET /api/{type}/channels/subagent-routing` | 返回持久策略、兼容状态、脱敏的有效渠道视图及 revision |
| `PUT /api/{type}/channels/subagent-routing` | 原子保存默认模型和完整序列，携带 GET 返回的 revision |

接口仅接受四类文本协议，沿用管理鉴权。静态路由应在 `/:id` 路由前注册；两端 API 客户端同步类型。

服务端拒绝跨协议 UID、重复 UID、非法字段和过期 revision；冲突返回 409。revision 覆盖本协议渠道集合及策略相关配置，不因指标刷新变化；比较与写入在同一配置锁中完成。

使用现有 ConfigManager 保存、备份及热重载机制；以副本校验并写盘成功后再发布内存配置，失败不得出现半更新。新增 map/slice 必须同步深拷贝、变更检测、导入导出与备份恢复。

模型预览复用实际执行的模型解析函数；未知模型允许保存，运行时仍遵守已有未知能力保护。管理接口不返回真实 Key，也不在保存策略时发起推理或能力测试。

## 5. 请求识别、模型解析与调度规则

实现统一的请求角色判定和策略解析函数，将原请求模型、有效角色、策略来源与配置快照贯穿候选筛选、执行、重试和日志。

### 5.1 识别门槛

- Codex：沿用 `client_metadata.x-openai-subagent` / `x-codex-parent-thread-id` 的精确信号。
- Claude Code：沿用现有 session 标记与 `X-Claude-Code-Agent-Id` 的精确组合。
- `Confidence=heuristic` 只用于观测，新策略不得据此切换模型或渠道；未知角色继续普通请求。
- 日志记录观测角色与是否应用策略，避免把「疑似子代理」显示成已经改模。HTTP 和 Responses WS 使用同一判断，不能只在 handler 外层检查后又被 `WithAgentModel` 覆盖。

### 5.2 模型与候选链

1. 请求进入时固定配置快照，确定是否应用该协议的新策略；一次请求的重试不混用保存前后版本。
2. 精确子代理且设置默认模型时，以该值替代原请求模型参与模型支持、上下文和能力筛选，再解析各渠道映射后的实际模型。
3. 默认模型为空时保留原模型及现有模型候选链行为；所有候选仍限制在子代理启用集合。
4. 默认模型非空时，渠道失败只在该模型对应的子代理渠道之间转移，不再回退原请求的模型候选链；既有尝试次数和时间预算继续有效。
5. 重定向只修改请求级配置副本和必要模型字段；保持原始请求模型用于日志，不能回写持久 `ModelMapping`。

候选顺序：子代理参与集合 → 路由前缀 / 模型 / 上下文 / 能力及共享运行限制 → 合法显式指定渠道 → 子代理自身亲和 → 子代理序列及现有故障转移。

- 在正常选择、最佳优先级恢复、soft-skip、degraded 和故障转移等分支统一使用有效参与集合与顺序。
- 普通促销优先级不改变新子代理序列；模型映射、限流、Key 轮换和预算保护复用现有机制。
- `X-Channel` 仍用于明确指定渠道，但不能绕过子代理参与关闭、暂停、模型或上下文限制；指向禁用候选时明确失败。
- 单渠道模式也执行角色、参与与模型规则；不能从「当前渠道直连」绕过独立策略。
- 子代理池全部关闭、不可用或不支持目标模型时明确返回无可用渠道，不自动回到普通池或主代理模型。

### 5.3 Responses 续聊保护

保留主/子角色隔离的亲和与成功渠道恢复。相同策略下的加密续聊不因普通渠道排序、闲置或上下文分桶变化失去成功渠道；成功源仍需满足当前子代理参与及硬限制。

策略修改后，新任务采用新策略；已有成功状态的加密续轮优先保持可兼容的原实际模型和来源。若修改模型或关闭来源会迫使无法证明兼容的迁移，则明确提示恢复原策略或新建任务；不得删除密文、降为普通文本或静默改发强模型来规避错误。

分别覆盖 `encrypted_content`、sealed task 和 `previous_response_id` 的实际路径。HTTP 与 WS 两轮验证必须独立完成，不能仅依据通用调度测试宣称两者都保存了成功来源。

## 6. 兼容迁移与驾驶舱收敛

新版本读取旧配置时不自动启用独立策略，保证升级本身不改变已有流量。首次进入子代理 tab 时生成转换草稿：

| 旧配置 | 转换草稿 |
|---|---|
| 全部渠道未设置子代理模型 | 默认「保持原请求模型」；顺序和参与状态按旧配置初始化 |
| 所有非空子代理模型一致，其他渠道为空 | 建议统一值，同时说明原空值渠道将改用统一模型；保存前仅预览 |
| 存在不同子代理模型 | 显示旧渠道与模型列表，要求明确选择统一模型，不按多数值自动覆盖 |
| 已有手动 override | 展示该协议存在旧人工排序，保存新策略后停用旧 override，不转换成全局默认顺序 |

只有明确保存才激活新策略。初始化时 `status=disabled` 的渠道参与关闭，其他渠道保留位置；共享暂停仍显示不可用。取消或保存失败均继续旧行为。

激活后的兼容规则：

- 该协议不再读取旧的渠道 `SubagentModel`；旧字段和 override 数据暂存用于回退，不再参与新策略。
- 该协议旧驾驶舱主/子代理手动排序均停用，普通请求使用普通渠道列表排序；管理端返回清楚的转换结果。
- 旧客户端向已激活协议写入 `SubagentModel` 或人工 override 时返回 409 与迁移说明，不能静默成功。其他渠道字段仍可正常更新。
- 未激活协议继续旧行为，并保留必要兼容入口；新安装通过同一页面明确保存策略。

驾驶舱收敛安排在两端独立 tab 和日志验收之后：

1. 已转换协议移除接管、解除接管、主/子序列与 TTL 操作；未转换协议仅保留迁移所需的旧入口。
2. 将角色、原模型、默认模型、实际发送模型和选路原因集中到请求日志；已有父子关系数据按需复用，不重建一套会话看板。
3. 全部需要人工调度的协议转换后移除驾驶舱导航，旧 Web `/conversations` 跳转渠道页；Desktop 处理旧 `cockpit` tab 的持久值、侧栏及事件导航。
4. 保留 conversation tracker、成功来源持久化与调度亲和。旧 override API 的读取可暂留兼容，彻底删除及旧字段清理另行评估。

更新两端帮助文案与操作说明，明确「保存一次，后续精确子代理自动执行」。

## 7. 实施阶段与依赖

依赖顺序：P0 → P1 → P2；P3/P4 可在 P1 接口稳定后分别开发，必须在 P2 完成后联调；P5 依赖 P2/P3/P4 全部验收。

| 阶段 | 工作 | 完成条件 |
|---|---|---|
| P0 环境与基线 | 检查 worktree、父分支漂移、两端依赖/锁文件、本地配置及端口；确认旧行为和测试基线 | 环境可构建，既有缺陷与本次改动分开记录 |
| P1 配置与 API | 定义协议策略、UID 校验、原子保存、revision、兼容状态与两端类型 | 保存/热重载/并发/导入恢复测试通过 |
| P2 请求执行 | 统一角色与模型解析，独立候选顺序，覆盖 HTTP/WS、单渠道、fallback、亲和与续聊 | 上游实际收到预期模型，主代理与候选集合隔离 |
| P3 Web | 独立 tab、草稿保存、模型预览、开关排序、旧配置转换；移出编辑框模型项 | 真实页面完成从配置到发送模型的闭环 |
| P4 Desktop | 对应独立 tab、API 客户端和模型读取；处理旧 tab 与驾驶舱入口 | Desktop 使用同一后端策略并完成闭环 |
| P5 收敛与交付 | 按迁移状态下线驾驶舱人工调度，补日志与文档，执行集成矩阵 | 用户无需逐会话调度；未转换配置和回退路径可用 |

P0 的前端 worktree 检查应在开发前完成：

- 按现有脚本使用 Bun 和现有 `bun.lock`，不新增或切换锁文件；两端分别检查依赖可用性，缺失时在当前 worktree 安装。
- 比较 main / 父分支与当前 HEAD。该 lean 分支有明确裁剪目标，不直接同步 main；仅在实际父分支可 ff-only 且不引入裁剪内容时同步，其他差异先评估。
- 检查 `.env.local`、`.env.development` 及本地配置是否需要初始化；不复制真实密钥进提交。
- 确认开发端口不会冲突，两端缓存和生成目录不与其他 worktree 混用。
- 已有未提交改动保持原样；仅提交本任务文件，不自动 stash、切分支或改写历史。

P2 必须将成功续轮所需的实际模型、来源和策略标识纳入现有请求/成功来源记录，并确认子任务身份粒度；不能只记录「当前正在尝试的渠道」。实现中如需新增持久字段，同步缺省读取与深拷贝。

实现和测试可以分工并行，但配置、共享模型解析与调度核心由一个修改者负责；Web/Desktop 各自独立修改，主执行者核验上游模型、共享改动和最终验收。

每阶段保持可独立评审的本地提交；按仓库要求自动提交已验证改动，推送、分支操作和运行实例重启仍按现有授权规则处理。

## 8. 验证与验收

后端以表驱动测试和 `httptest` 隔离上游验证，至少覆盖：

- 配置缺失、空模型、模型 trim、混合旧模型转换；重复/过期/跨协议 UID、并发 revision、磁盘失败与热重载。
- 精确子代理切换模型；启发式、未知角色和主代理保持普通行为。HTTP 与 WS 判定一致。
- 普通渠道关闭但子代理开启可执行；子代理关闭不影响主代理；暂停、熔断和 Key 禁用仍拦截。
- 主/子独立排序；普通重排、改名、复制、删除不串 UID；亲和恢复和所有兜底不越出子代理池。
- 大类映射、具体模型、原模型保留、未知能力、上下文/输出限制、图片/工具能力及显式指定渠道。
- 第一渠道失败后第二渠道收到正确模型；重试不被旧候选链、普通促销或旧 override 改回主模型。
- 单渠道模式及四文本入口的流式/非流式执行；Images/Vectors 维持既有行为。
- Responses HTTP/WS 两轮、加密输入不变、`previous_response_id`、闲置/分桶/保存恢复、策略修改时的兼容保护。

前端轻量单测集中在草稿、UID 排序、冲突处理和异步模型选择；不新增仅复述模板的测试。两端使用真实页面检查 tab、选择/手输模型、开关、拖动/移动按钮、保存/取消、刷新和错误恢复。

完整验收场景：

1. 普通模型 `astra`；子代理设置 `sol`，启用 A/B 并调整顺序，保存后刷新。
2. 发起主代理请求和带精确标记的子代理请求：主代理沿用原策略，子代理实际上游模型等于对应渠道的 `sol` 映射值。
3. 让 A 的隔离上游返回可重试失败：B 接续请求，仍使用子代理默认模型；日志可追踪所有尝试。
4. 关闭全部子代理渠道：子代理明确失败，主代理正常；恢复开关后子代理自动恢复，无需驾驶舱接管。
5. 分别在 Web/Desktop 完成配置与请求闭环，核对日志里的原模型、策略模型、实际模型、角色和选路理由。
6. 旧配置未保存转换时维持原执行；转换后旧人工排序不再影响结果；回退备份后旧行为可恢复。

## 9. 风险与回退

| 风险 | 处理 |
|---|---|
| 启发式误判把主代理降级 | 新策略只接受精确角色；日志保留识别置信度 |
| 低阶模型不支持工具、图片或所需上下文 | 复用实际模型能力和请求硬约束；无候选时明确失败 |
| 普通排序、促销、override 或重试越过独立策略 | 集中解析有效策略，在所有调度分支复用同一候选集合 |
| 普通渠道重排后策略指向错误渠道 | 引用 UID，管理保存校验 revision，禁止持久引用 index |
| 加密历史跨模型/上游失效 | 保留成功来源与兼容模型，覆盖实际 HTTP/WS 续轮，不改写密文 |
| 两端保存或旧客户端覆盖策略 | 同步类型、原子保存、冲突反馈；已迁移字段拒绝旧写入 |
| 提前移除驾驶舱使旧配置无入口 | P5 在两端替代流程通过后执行，按协议迁移状态收敛 |

回退方案：保存前使用现有配置备份机制；需要撤销独立策略时，通过备份恢复该协议策略及旧渠道/override 状态，并验证旧调度恢复。不能只降级程序而保留新策略，旧版本会忽略字段并可能重新使用强模型。

回退只影响本功能的策略与界面入口，不删除请求日志、conversation tracker、成功来源或真实 Key。生产配置恢复和版本切换需明确授权，不由本计划自动执行。

完成定义：两端均能在渠道列表配置默认模型、开关和顺序，精确子代理的实际上游请求及失败重试符合策略，主代理和 Images/Vectors 不受影响；旧配置可迁移和回退，驾驶舱不再承担已转换协议的日常人工调度。
