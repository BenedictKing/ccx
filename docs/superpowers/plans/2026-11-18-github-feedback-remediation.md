# GitHub 用户反馈全量处理方案（网关约定）

日期：2026-11-18  
范围：`BenedictKing/ccx` 的 36 个开放 issue、3 个 discussion、8 个开放 PR。  
基线：本地 `codex/v3-lean-from-2.9.37`（`b0da2056`）；远端 `main` 为 `3a08db97`，最新 Release 为 `v2.9.37`。  
目标：把已写代码但尚未交付的修复、尚未闭环的缺陷、新需求和外部依赖分别处理，形成可执行、可验收、可关闭的清单。

## 1. 处理原则与完成定义

1. **先交付已有修复，再开发新能力。** 当前分支已有相关实现的 20 项先进入验收批次；#294 仍需完善普通渠道的配置流程。通用改写、Voice、智能路由和定时切换不阻塞缺陷修复版本。
2. **不以回复、PR 可合并或本地提交作为解决依据。** 必须同时具备代码、针对性回归测试、要求的原始场景验证和包含修复的发布版本。
3. **不为关闭 issue 而改需求。** 原始问题与追加需求分开跟踪；外部上游限制、无法复现和暂不规划均可关闭，但必须说明理由与后续触发条件。
4. **先复现再修改。** 尚未定位的缺陷先保存脱敏请求、响应、选路轨迹和版本信息，构造失败用例后再改实现。
5. **所有实现基于当前 lean 分支。** 用户在本轮明确将自行合并到 main 并更新版本；本任务完成 lean 本地实现与验证，不自动同步 main、推送、发布或关闭 GitHub issue/PR。交付记录提供主分支合并后的复核清单。
6. **不触碰运行实例。** 验证使用 `httptest`、隔离配置和独立构建产物；需要加载新代码时由用户手动重启其实例。

每项反馈必须落入以下一种终态：

- `released`：修复或功能已发布，验收通过，issue 附版本与提交后关闭。
- `external`：已证明是上游或客户端限制，文档说明可行的 CCX 配置与边界后关闭。
- `needs-repro`：缺关键证据，明确列出补充材料；两个发布周期仍无信息可关闭，后续可重开。
- `not-planned`：与当前产品边界冲突，记录替代方案和重新评估条件后关闭。
- `accepted-future`：独立功能评审通过，有独立设计、验收门和跟踪项，不混入缺陷发布。

## 2. 统一网关约定

### 2.1 原生透传与跨协议转换

- Messages→Claude、Chat→OpenAI、Responses→Responses、Gemini→Gemini、Images→Images、Vectors→Vectors 默认保留请求正文、非流式响应和 SSE 原始字节。
- 只有模型映射、参数覆盖或兼容开关明确启用时才修改对应字段；JSON 改写保留大整数精度、未知字段、显式 `false`、空对象及合法空字符串。
- `additional_tools` 原生路径原位透传；跨协议或显式兼容路径才提升为顶层工具。namespace/custom 工具保留名称、namespace、ID、strict 和空 input。
- 客户端侧 `tool_search` 等类型只在目标上游不支持时剥离或代理，并同步修正 `tool_choice`；原生支持的链路不得一律删除。
- 查询参数保留重复值与编码；路由参数优先，网关鉴权 query `key` 不转发给上游。
- 原生流解析仅用于预检、指标和会话记录，不默认合成 completed、补 usage 或规范化事件；推理续轮折叠必须显式开启。
- 跨协议响应必须形成目标协议合法终态；无法转换的未知语义应显式记录，不得返回空 200、重复尾帧或伪造成功。
- 协议适配优先使用能力元数据和通用规则，禁止仅凭模型名硬编码绕过缺陷；确需模型特例时必须有官方依据和回归样本。

### 2.2 调度、故障转移与模型回退

- 客户端取消、下游 broken pipe/写方向 connection reset 不计为 Key、模型或渠道失败；读上游时的连接重置仍按上游故障处理。
- 请求 schema、鉴权和其他确定性 4xx 不因错误文案中的“重试”等词触发盲目 failover；429、配额、模型缺失和 5xx 按既定分类换合格 Key 或渠道。
- 渠道关闭自动熔断只绕过自动熔断，不绕过鉴权/余额拉黑、显式暂停、限速 cooldown、上下文与模型能力过滤。
- 跨模型回退仅执行用户显式配置的有序候选，并受 `MaxAttempts`、`MaxWaitSeconds` 约束；不得因“质量评分”静默替换用户模型。
- 同一渠道多目标模型回退复用 `ModelFallbackPolicy`，每次尝试重新计算资格、映射和工具上下文，不复用上一次失败请求的可变状态。
- 已建立上游流后发生客户端可见输出时，不盲目切换到另一渠道重放；只对可安全重试的阶段 failover。
- `previous_response_id`、加密续轮和 Trace 亲和必须保持会话语义；跨模型或跨协议回退时从快照重建请求，不修改持久历史。
- Copilot 服务身份与实际协议分离：按映射后的模型解析 endpoint、HTTP/WS 传输、认证与响应解析器；发现、能力测试与运行时复用解析器。能力缓存按账号凭证、API 地址、代理与 TLS 配置隔离，有期限并合并并发刷新；显式非默认 Base URL 优先于 token 返回的默认地址。缺元数据仅保留有诊断的历史默认值，不声称已验证。
- Responses 加密历史不能凭空解密；跨协议只允许可重建的明文历史快照。缓存未命中或存在不可转换的密文时，尝试其它兼容候选或返回明确错误，不删除密文后伪装续轮成功。
- 选路日志必须能回答“请求模型→有效模型→实际模型、候选为何被过滤、尝试了哪些 Key/渠道、为何最终失败”。

### 2.3 配置、用量、日志与安全

- Base URL 默认补协议版本前缀；显式尾部 `#` 表示保留完整精确路径，不再追加 `/v1`。UI、后端构造和指标身份必须采用同一语义。
- 自定义模型名、Base URL 和 Key 均可显式编辑；自动发现只提供候选，不覆盖用户输入。映射按协议独立保存并支持重启恢复。
- Desktop 写 Codex/Claude/OpenCode 配置时保留用户认证模式、未知字段和手工修改；写入失败可恢复，不以网关配置反写直连配置。
- usage 采用目标客户端协议的定义；缓存 token 不重复扣减，所有非负整数字段不得输出负数。低质量 usage 估算必须保留缓存计数并记录替换原因。
- 自定义渠道价格优先于注册表兜底，历史与全局统计采用同一计算口径；价格缺失时显示未知，不伪造零成本。
- 日志和 issue 回复只使用脱敏 Key、Authorization、令牌和请求样本；不下载或推荐用户附带的第三方补丁压缩包。
- Images/Vectors 不套用文本协议 capability-test；新能力先明确六协议各自支持范围，不声称全协议通用。
- 新配置必须兼容 v2.9.37 快照，提供加载→保存→重启回归；失败时不写坏原配置。

## 5. 未闭环缺陷实施方案（11 项）

### 5.1 发布前优先处理

**#273 Copilot 模型级 endpoint 与原生工具**

1. 在 Copilot 发现结果中保留每个实际模型支持的 `/responses`、`/v1/messages`、`/chat/completions` 和 WS 能力，形成规范化只读能力表。
2. 新增共享的“映射后模型→上游 endpoint”解析器，discovery、capability-test 和运行时调用同一入口；禁止 `ResponsesProvider` 对 Copilot 无条件拼接 `/responses`。
3. Responses 客户端映射到 Claude/Gemini 等模型时，先选 endpoint 再进入对应转换器；失败重试重新构造工具上下文和请求体。请求与响应共享实际协议，认证/计费身份仍归原 Copilot 渠道；WS 仅在模型声明 `ws:/responses` 时使用原生连接，否则走已有 HTTP bridge。
4. 无 endpoint 元数据时使用显式渠道覆盖或保守默认，并在诊断中显示来源，不伪造“已验证”。
5. 验收：GPT→Claude 示例走 Messages/Chat 并返回合法 Responses；原生 Responses SSE 不误判空流；四类客户端入口覆盖流式/非流式；工具历史、缓存隔离、认证头、精度和 WS 续轮有回归。直接或快照中的密文无法跨协议转换时必须明确失败，不能伪造历史；真实账号验收独立记录。

**#275 GPT‑5.6 Chat 工具调用**

1. 用同一上游分别保存 5.5/5.6 的脱敏请求、响应和工具结果，比较 CCX 出口字节，定位差异来自网关还是上游能力。
2. 原生 Chat 默认透传；只有显式兼容开关才转换自定义工具，禁止按“5.6”名称直接删除工具。
3. 验收：终端命令、插件、并行工具、工具结果续轮和流式终帧均成功；5.5 不回归。若官方 Chat 本身不支持该工具，则返回明确能力错误并文档化，而不是静默降级成只能聊天。

**#282 `<commentary>` 泄漏**

1. 用选路日志和原始上游响应确认标记由上游模型生成还是 CCX 转换器生成。
2. 若为网关包装/解析残留，删除生成点并补流式跨 chunk、非流式和多轮回归；若为上游正文字面量，不为掩盖上游问题而通用删除用户内容。
3. 验收：DeepSeek 映射的 Terra/Luna 请求不暴露网关内部标记，正常文本、工具参数和 reasoning 不丢字。
4. 原帖同时报告“输出该内容后就结束”，必须保存工具增量、停止原因和完整终帧，区分真实结束、解析丢失与工具续轮中断；只清理标签不能关闭此项。正文中的字面标签不触发自动续推理或额外收费请求。

**#297 GLM＋K3 长任务 503/超时**

1. 用两个假上游复现限流、超时、503、长流和客户端取消，记录每个候选被跳过或失败的原因。
2. 要求渠道接力使用显式模型候选；检查重试预算、Trace 亲和、熔断和上下文过滤是否共同造成“有渠道但无候选”。
3. 只有仍有合格候选却提前返回 503 才修调度；真实超时则展示首字节/工具调用/流空闲等具体阶段，不统一改写为渠道不可用。
4. 验收：主渠道可恢复故障时按预算接力，所有候选确实失败时返回最后有效诊断；长任务和 subagent 不互相污染亲和与熔断。

**#263 Chat→Responses 上下文用量**

1. 固定 llama-server 请求/响应样本，分别记录上游 prompt/completion/total、缓存和 CCX Responses usage，先区分上游错报与转换错报。
2. 低质量开关下复用统一本地估算，偏差阈值和缓存保留规则与现有实现一致；不得为凑客户端显示而篡改真实总量。
3. 验收：Chat 转换与原生 Responses 在同等历史下误差有解释且不再持续放大，所有计数字段非负；Codex App 自身额外预算差异写入边界说明。

**#294 普通渠道内多模型接力**

1. 当前 `ModelFallbackPolicy` 是全局候选链，主要由站点向导生成，普通渠道仍使用单目标映射；该项不能归为已完成。
2. 复用现有候选与预算执行器，增加普通渠道的有序候选配置与 Web/Desktop 编辑入口；保存、预览、热重载和重启保持一致。
3. 明确“同渠道换模型”和“同模型换渠道”的优先级，预览实际尝试顺序；不把全局策略误报为渠道绑定策略。
4. 验收覆盖同站 Flash→Pro→Grok、另一站候选、Key 轮转、预算、删除撤销与历史重建；未启用时不换模型。

## 6. 新需求处理方案（4 项）

### 6.1 #247 请求体条件改写

**建议：单独立项，先实现受限的规则引擎，不做任意脚本。**

- 配置挂在渠道上，仅对显式启用规则的请求生效；无规则的原生请求仍走字节透传。
- MVP 仅支持点分字段路径、`==/!=/>/>=/</<=/contains/startsWith/endsWith/exists` 条件和 `set/delete` 动作；规则按数组顺序确定性执行。
- 仅允许改写业务 body 白名单，禁止修改鉴权、URL、headers、流式标志和会话内部字段；不引入模板执行、外部脚本或响应改写。
- 保存时做 schema 校验、路径冲突检测和最大规则数/嵌套深度限制；提供脱敏 dry-run diff，运行日志只记规则名和结果。
- 条件显式选择原始客户端快照或转换后的上游 body；默认读取原始快照，因此 `thinking.budget_tokens` 不因转换而消失。动作只写上游 body，位于协议转换/专用参数覆盖后、最终鉴权与发送前。每次重试从原快照重新执行，不累计改写；预览同时显示实际模型、条件来源与最终正文。
- 验收：issue 的 DeepSeek/GLM reasoning 示例、非法规则、未知字段、大整数、热重载、重启和六协议边界均有测试。

### 6.2 #280 Voice Chat / `/v1/live`

**建议：先做协议调研和最小原生代理原型，未确认前不宣称支持。**

1. 获取 ChatGPT 实际 `/v1/live` 的传输方式、鉴权、事件、音频格式、中断和会话恢复约定，保存脱敏协议样本。
2. 若是有状态 WebSocket/双向音频，新增独立 handler 与上游会话生命周期，不复用普通 Responses HTTP 流；仅路由到明确支持该能力的原生渠道。
3. 客户端与上游断开必须双向传播，设置空闲/总时长和音频背压限制；熔断与指标只统计真实上游失败。
4. 不支持时返回明确 404/501 和能力诊断，不返回空 200，不跨协议模拟语音，不把音频明文写日志。
5. 验收：建连、双向音频、打断、续轮、取消、上游错误、用量与多渠道路由分别测试；调研确认非公开或不可代理时以 `not-planned` 回复并保留重新评估条件。

### 6.3 #295 按复杂度智能路由

**建议：默认关闭，使用显式 `auto` 路由策略，不能改变普通模型请求语义。**

- 用户为每个协议配置允许使用的候选模型及顺序、最大成本和超时；只有请求该策略别名时才启用分类，未命中或低置信度走用户指定默认模型。
- 第一阶段用可解释规则处理明确的 agent 角色、工具需求、上下文长度和用户 hint；内容复杂度分类作为后续可选阶段，不先引入 benchmark/质量评分平台。
- 若使用模型分类，只能调用用户授权的可信官方或本地分类器；中转站/公益站不读取用户内容，分类失败不阻断默认路径。
- 选路结果记录策略、分类依据、置信度和实际模型；不得把自动路由与普通 `ModelFallbackPolicy` 混为一谈。
- 验收：未开启时字节和选模不变；简单/复杂样本路由符合策略；分类器超时、无候选和回退均确定性工作，成本与次数有硬上限。

### 6.4 #299 峰谷价格定时切换

**建议：先实现“按时间表选择用户已授权的模型候选”，不自动修改上游价格。**

- 在显式路由策略上增加命名时区、时间窗口和对应候选顺序；首版不用任意 cron，避免日历语义失控。
- 新请求进入时解析一次当前窗口；进行中的流和续轮不因时间切换中途换模型，Trace 亲和按策略版本/窗口隔离。
- 窗口重叠按配置顺序或更具体规则确定性处理，无匹配窗口使用默认候选；热重载只影响后续请求。
- UI 显示当前生效窗口、下一次切换时间和实际模型；价格只用于展示或用户设置的策略选择，不从未知价格推断真实成本。
- 验收：跨午夜、DST、非法时区、重叠/空窗口、重启和进行中请求有测试；关闭功能后完全保持现有多渠道调度。

## 9. 验证矩阵与发布门禁

### 9.1 按受影响路径选择用例

- **请求构造**：默认原生、显式映射、显式兼容、跨协议四条路径分别断言实际上游 body、URL、query 和 headers。

## 10. Issue 回复、关闭与发布计划

1. **建立单一跟踪状态。** 本地记录 issue、lean 提交、针对性测试、原场景状态与合并后复核项；由用户按需同步 GitHub 标签和回复，本任务不自动写入。
2. **用户合并与发布。** 先完成 lean 本地验证与提交；用户自行合并 main、更新 `VERSION`/`CHANGELOG.md`、推送与发布。发布范围按已经验收的修复确定，不等待无关外部环境问题。
3. **发布后逐项回复。** 用户确认实际发布版本后，回复应附 Release、修复提交、配置变化及验证结果；需要原环境确认的保持 `pending-verification`，不能把 lean 本地通过直接写为 main 已解决。
4. **拆分追加需求。** #245 的 OpenAI OAuth、#268 的独立建议和 #273 的不同子问题分别链接新 issue，避免原始帖永久无法关闭。
5. **外部或暂不规划项也闭环。** 写明 CCX 已做和不能做的部分、可行替代方案、重新打开所需证据，不以沉默保持开放。
6. **功能项独立排期。** B4 四项分别形成 RFC 和原型评审；未通过评审前保持 `accepted-future` 或转为 `not-planned`，不进入缺陷修复 Release 的完成声明。
7. **发布核对。** Release assets、签名和实际 `/health` 的 `version.gitCommit` 与候选提交一致；运行实例由用户自行升级或重启。

最终完成标准不是“36 个都写着 fixed”，而是每个都有明确终态，且状态与代码、测试、Release 和用户反馈一致。
