# 精简 3.0 重建计划

## 基线与目标

- 基线：`v2.9.37`（`78352226`），在独立 worktree 开发，不改当前 `main` 或运行中的服务。
- 核心路径：用户接入站点账号，分别为 `messages`、`responses`、`chat` 配置渠道、分组、Key 和显式模型映射。
- 站点账号仅共享管理凭证及站点身份；协议渠道的 Key、分组、模型和故障转移配置互相独立。
- 自动化负责可验证的发现、建 Key、同步和重试；模型及可接受的替代模型由用户选择。

## 实施顺序

1. 锁定 2.9 基线：Web/Desktop 构建、后端/Desktop Go 测试、协议级渠道与模型映射回归。记录原版失败，不混入移植问题。
2. 整理 3.0 改进清单：按用户路径挑选协议转换、流式安全、故障分类、Key 恢复等修复；逐项移植并配回归测试，不按提交批量搬运。
3. new-api 接入：按所选协议验证账号、该协议目标模型与分组的可用性；建或导入分组 Key，建立独立渠道，支持定期对账与失效恢复。仅持有推理 Key 时走导入路径，不声称可代建远端 Key。
4. sub2api 接入：先支持推理 Key 导入；确认可用的用户级管理认证后，再实现账号校验、分组查询及远端建 Key。认证能力不足时明确保留人工步骤。
5. 接入验收：所选协议完成真实请求及必要的流式/工具调用验证后才显示可用；失败要定位到凭证、分组、模型、协议或客户端配置。
6. 故障策略：默认只在同一目标模型的可用 Key/渠道间重试；跨模型降级必须由用户显式允许，流已输出后不得伪装成透明重试。

## 不纳入本轮

- 基于任务内容、智力基准或价格预测自动选模型。
- 将不同协议强制合并成一个可编辑渠道或共享一套分组/Key 策略。
- A/B 双发、自动发布控制、复杂质量评分与未证明改善核心路径的观测体系。

## 数据与验证边界

- 当前 3.0 配置可能只保存 `channelsV3`；2.9 无法直接读取。上线前需离线导出为协议数组，校验 Key/分组/映射/顺序，并保留原配置与数据库备份。
- 新 worktree 使用独立依赖、构建产物和测试配置；不得指向当前运行实例的数据目录或占用其端口。
- 每个阶段至少通过相关 Go 测试、Web/Desktop 类型检查与构建；接入阶段追加 new-api/sub2api 假站点契约测试和真实站点手动验收。
- 只有协议级接入、故障转移、数据迁移三项验收都通过，才讨论替换现有主线；回滚使用保留的旧二进制和原数据副本。
