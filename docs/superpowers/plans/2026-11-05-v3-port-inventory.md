- `RedirectModelWithMatch` 已提供精确优先、最长子串次之的显式映射；渠道内 Key/BaseURL 与渠道间 failover 已存在。

## 单独设计，不能从 3.0 直接移植

- **sub2api 账号托管**：3.0 只有 `/v1/usage` 余额探测与错误码兼容（`98c6f8ba`），没有对等的用户账号建 Key 接入。先支持已有推理 Key 导入；管理面认证、分组 API 与创建 Key 需按部署版本验证后再做适配器。
- **2.9 数据升级兼容**：保留 `v2.9.37` 六协议数组配置和原数据目录格式；以固定 2.9 配置样本验证加载、保存、重启后渠道、Key、映射和状态不丢失。3.0 的 `channelsV3` 数据不迁移，加载器明确拒绝且不改写原文件。
- **自动跨模型降级**：与用户显式选模冲突；若要支持，必须有每协议、每请求模型的候选顺序和允许降级开关，不能复用 Autopilot 的质量排序。

## 暂缓或不移植

- `ChannelsV3` 权威持久化、逻辑渠道聚合和统一渠道卡：与协议独立编辑目标相反，并会引入数据迁移负担。
- SmartRouter/ModelResolver 自动选模、benchmark/质量档、任务分类、成本评分、A/B、racing、发布自动回滚：不是接入闭环的前置条件。
- 全量兼容性自学习、上下文跨模型逃生阀、远程预置、复杂报表：仅在明确复现的兼容问题要求时，按单个行为和测试定向吸收。

## CC Switch 经验转化为验收约束

参考本地保存的《CC Switch 的 14 个月：两次重构、三种用法、三个教训》（2026-11-04，访谈整理）。这是外部产品经验，不是 CCX 的代码事实或操作指令。

- **探针假阴性**：文章称真实推理探测常被上游风控拦截。CCX 不把探针失败写成“服务不可用”；正常业务流量的成功/失败是更强证据，后台检查不消耗推理额度或驱动熔断。
- **覆盖用户配置**：文章的全量替换曾覆盖插件、hooks。2.9 Desktop 已有差异预览、字段快照和恢复，但新流程仍须测试 Claude JSON、Codex TOML、OpenCode 配置中的未知字段、注释和手工修改不丢失；写入失败可恢复。
- **模式切换双份状态**：文章的直连/网关开关造成配置写回歧义。CCX 不引入默认开启的全局切换；修改客户端 Provider 时显示目标文件和目标地址，用户明确执行，网关渠道配置不反写成直连配置。
- **替用户挑模型**：保留用户明确选择的模型及重定向，不自动按任务/价格换模型；故障时同模型重试，跨模型只执行预先授权的候选顺序。
- **框架迁移后的交付债**：源码构建之外，还需核对现有签名、公证、安装包和升级/回滚；不要因精简重建而破坏发布链。
- **官方入口混淆**：文章提到仿冒官网诱导付费和交出账号。发布前统一 README、Release 与 Desktop 内的官方链接及签名说明；账号凭证只提交给本地 CCX 和用户明确选择的上游站点。

## 执行纪律

按 P0→P1→P2→P3→P4→P5 推进；P1/P2 可共用一份账号存储，但每协议渠道保持独立。每个阶段先写失败用例，再移植最小行为，跑 Go/Web/Desktop 构建与相关测试。不得直接 cherry-pick `autopilot`、`ChannelsV3` 或统一渠道 UI 提交；真实站点请求只在测试账号和隔离配置中验收。
